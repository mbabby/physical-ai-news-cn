# Phase 4 Community Evidence Flywheel Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a GitHub-native evidence flywheel that publishes at most five safe, two-minute verification tasks, records accepted contributions append-only, and sends accepted evidence back through the daily verification pipeline without bypassing public evidence gates.

**Architecture:** Add a focused `src/community-evidence/` domain with exact runtime contracts, deterministic seed generation, a pure WIP/lifecycle planner, a GitHub Issues adapter, append-only contribution projections, and public-view formatting. The daily generator remains the only publisher of repository artifacts and stages every new JSON/page output in the existing `FileTransaction`; the weekly workflow only applies Issue actions generated by the pure planner. Existing Watchlist seed generation remains as an internal input until migration is proven, but it is no longer the public task contract.

**Tech Stack:** TypeScript 5, Node.js 24, `tsx`, Node test runner, GitHub Actions, GitHub CLI, static HTML/CSS/JavaScript, existing `FileTransaction` and exact release validators.

## Global Constraints

- Do not add an external database, account system, notification service, or third-party task backend.
- Keep `accepted-evidence` as a human approval signal only; it must never publish a fact directly.
- A public task has exactly one `targetField` and one canonical company, event, or paper subject.
- Public artifacts must not contain candidate IDs, internal scores, ranks, model responses, raw comments, secrets, or unsupported conclusions.
- Unknown remains `unknown`; never render it as “未融资”, “没有部署”, “没有代码”, or another negative fact.
- Maintain at most five open tasks, reserve one slot for each of the three task categories when eligible seeds exist, mark inactive tasks stale after 7 days, and close them after 14 days.
- Task creation must be idempotent by stable public task ID; accepted, stale, closed, and superseded task history remains traceable.
- Contribution history is append-only; correction and withdrawal add state events instead of rewriting history.
- GitHub/API failure or invalid remote data must retain the last known good public task and contribution projection.
- Keep all generated repository artifacts deterministic for fixed inputs and stage them atomically with existing daily outputs.
- Do not modify or commit the local untracked `.DS_Store`.

## File Structure

New focused files:

- `src/community-evidence/contracts.ts`: exact types, stable IDs, recursive validators, and public/private boundary checks.
- `src/community-evidence/task-seeds.ts`: converts three canonical candidate pools into sanitized one-field task seeds.
- `src/community-evidence/task-ledger.ts`: deterministic WIP, deduplication, stale, close, and version planning.
- `src/community-evidence/github-issues.ts`: fetches and normalizes the minimum GitHub Issue state without storing comment bodies.
- `src/community-evidence/contributions.ts`: accepted-evidence projection and append-only contributor state transitions.
- `src/community-evidence/publication.ts`: builds `site/data/community-tasks.json`, contribution summaries, and HTML-safe public views.
- `src/community-evidence/plan-issue-actions.ts`: CLI boundary that reads normalized artifacts and emits GitHub Issue actions as JSON.
- `site/contribute.html`: contribution center backed by the same ordered public artifact used by the homepage.

Modified integration files:

- `src/main.ts`: collect inputs, fetch/fallback Issue state, stage all evidence-flywheel artifacts in the daily transaction.
- `src/project-insights.ts`: retain old Watchlist seeds as internal compatibility input and remove public scoring from the review queue.
- `src/site-data.ts`, `site/app.js`, `site/index.html`, `site/styles.css`: public task and contributor modules.
- `src/validate-release.ts`, `src/runtime/validation.ts`: cross-artifact and append-only validation.
- `.github/workflows/materialize-review-issues.yml`: weekly WIP replenishment and Issue lifecycle application.
- `.github/workflows/daily-digest.yml`: provide repository/token context for Issue projection.
- `scripts/community-metrics.mjs`: evidence-task metrics without contributor ranking.
- `CONTRIBUTING.md`, `CONTRIBUTORS.md`, `README.md`, `community/evidence-review.md`: contributor contract and correction semantics.
