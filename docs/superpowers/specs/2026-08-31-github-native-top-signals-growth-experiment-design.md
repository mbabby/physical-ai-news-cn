# GitHub 原生 Top Signals 两周增长实验设计规格

## 1. 背景

`physical-ai-news-cn` 已经形成公司、资本、产品部署、技术路线、论文、信源健康与社区补证等数据能力，但外部反馈与传播仍然有限。2026-08-31 的基线为：

- GitHub Star 1、Fork 0、Watch 0；
- 近 14 天 GitHub 页面 24 次浏览、5 位独立访客；
- 417 次 Clone / 83 位独立克隆者受到 GitHub Actions checkout 污染，不作为真实用户指标；
- 公开系统维护 49 家公司、112 篇近 30 天论文与 40 个信源，但首页产业事件、Top Signals 与公司动量均为空。

当前问题不是继续扩充后台能力，而是验证一份高质量、可独立分享的决策内容能否通过 GitHub 原生渠道获得外部传播。

## 2. 实验目标

实验周期为 14 天，优先服务投资与战略研究者，使用唯一传播楔子：

> **《Physical AI 资本与产品部署 Top 5》**

实验成功必须同时满足：

1. GitHub Star 从基线 1 增长至至少 11；
2. 至少 3 位不同的外部用户公开分享或引用项目、某期 Release 或单条证据归档。

外部引用包括他人在 GitHub Issue、Discussion、PR、README 或公开博客仓库中的主动链接。项目作者、机器人、自动提交、项目内部链接以及同一用户的重复引用不计入。

本实验验证内容的 GitHub 传播性，不把 Star 等同于留存、付费意愿或投资决策影响。

## 3. 渠道与行为边界

实验只使用 GitHub 原生阵地：

- GitHub Release；
- README；
- 仓库内固定归档；
- Issue、Discussion 与明确接受项目推荐的资源目录。

不新建或使用项目 X、LinkedIn、微信公众号、邮件列表等外部账号。

允许在相关 GitHub 仓库和 Discussion 中互动，但必须满足：

- 先提供与当前讨论直接相关的事实、复现结果、纠错或结构化资料；
- 明确披露与 `physical-ai-news-cn` 的关系；
- 只链接对应证据条目或当期 Release，不统一导向首页；
- 不主动索要 Star，不发布重复评论，不进行批量低质量 PR；
- 对方规则禁止推广、没有邀请或讨论不相关时不得发布。

两周内最多选择 6 个高度相关的外部 GitHub 互动机会。

## 4. 实验节奏与冻结范围

- 第 1–3 天：建立候选池、完成实体归属、补证与排序；
- 第 4 天：发布第一期，必须经过人工确认；
- 第 5–10 天：观察传播、进行合规的外部 GitHub 互动并积累第二期候选；
- 第 11 天：第二期在满足全部门槛后自动发布；
- 第 12–14 天：统计 Star、外部引用与内容表现，形成继续、调整或停止结论。

实验期间冻结：

- 新增页面和大规模 UI 改造；
- 泛公司、泛论文和泛信源扩充；
- 与 Top Signals 传播验证无关的功能；
- 不影响日报、证据门禁、Release 或指标准确性的重构。

允许修复阻断日报、证据核验、发布事务或增长指标的严重缺陷。

## 5. Top Signals 内容合同

每期最多 5 条，少于 5 条时不得用低质量内容补齐。每条信号包含：

1. 稳定 `signalId`；
2. 一句话中文信号标题；
3. 明确公司主体与事件类型；
4. 两句以内中文事实摘要；
5. 事件日期与最后核验日期；
6. `A` 或 `B+B` 证据等级、独立来源数量与证据链接；
7. 明确标记的“为什么重要”研究判断；
8. 下一验证点；
9. 可解释的排序分解；
10. 当期周期、生成版本和内容校验值。

第一期和第二期都必须由同一结构化合同渲染，Release、README 与归档不得分别生成事实正文。

## 6. 公开硬门槛

候选进入 Top Signals 必须同时满足：

- 公司主体明确且通过现有实体归属校验；
- 事件属于融资、并购、产品发布、客户或真实部署；
- 原则上发生在近 30 天；
- 至少存在一手官方来源，或两项相互独立的可靠来源；
- 中文事实摘要完整，不包含占位文本；
- 金额、轮次、客户、产品与部署字段均有字段级证据或明确为 unknown；
- 来源不处于暂停状态，证据链接在发布前可访问；
- 不存在主体冲突、日期冲突、撤回或未处理纠错。

泛行业盘点、观点评论、单一发现层线索、无法核实的金额以及只有推测性措辞的内容不得公开。

旧事件只有出现新增融资确认、客户、量产或部署证据时才能再次入选，并必须标注本期新增证据。

## 7. 排序规则

硬门槛通过后按 100 分制排序：

- 产业与资本影响力：30；
- 证据质量：25；
- 时效性：20；
- 信息新增量：15；
- 对投资与战略判断的相关性：10。

排序还必须执行：

- 同一公司最多 2 条；
- 同一种事件类型最多 3 条；
- 同一主体、同一事件只保留一条；
- 同分时依次优先官方证据、更近的核验日期和更近的事件日期；
- 相同输入必须产生相同顺序，页面和 Release 不得二次排序。

如果只有 3 或 4 条达标，按实际数量发布；少于 3 条时取消自动公开。

## 8. 两期发布机制

### 8.1 第一期：人工审批

流程：

```text
候选池 → 实体归属 → 二次证据 → AI 草稿 → 自动校验 → 人工确认 → Release
```

人工审批支持逐条：通过、退回补证、修改表述、移出本期。没有明确批准状态时不得创建公开 Release。

### 8.2 第二期：自动发布

流程：

```text
候选池 → 实体归属 → 二次证据 → AI 草稿 → 自动校验 → Publication Gate → Release
```

自动发布必须同时满足：

- 至少 3 条合格信号；
- 每条主体、日期、类型、中文摘要与证据完整；
- A/B 级证据比例为 100%；
- 不含“暂无简介”“据悉”“或将”等占位或推测表述；
- 所有证据链接可访问；
- 发布前后生成结构化摘要与内容校验值；
- 固定输入重试不会生成重复 Release。

任一条件失败时只生成 Review 记录与明确失败原因，不得公开。之后的人工兜底不计为第二期自动发布成功。

## 9. 发布表面与单一事实源

- GitHub Release：完整 Top Signals，作为当期权威分享版本；
- 固定归档：保存结构化数据、渲染正文、证据、发布时间与校验值；
- README 首屏：只展示最新一期前三条与完整 Release 入口；
- Latest 入口：指向当前有效一期；
- Review 队列：保存未达门槛候选，不进入 README 或 Release。

发布顺序必须先创建并确认 Release，再更新 README 的最新一期入口。Release 失败时不得提前更新 README。

## 10. 最小组件边界

实验只新增或收敛五个独立职责：

- **Top Signal Selector**：读取现有事件与候选数据，执行公开硬门槛；
- **Top Signal Ranker**：计算可解释评分并执行多样性约束；
- **Release Renderer**：从同一合同渲染 Release、归档和 README 摘要；
- **Publication Gate**：区分第一期人工批准与第二期自动门禁；
- **Growth Snapshot**：每日记录 Star、Release 访问与外部引用。

数据流保持单向：

```text
现有抓取与候选层
  → 实体 / 证据核验
  → Top Signals 选择与排序
  → 结构化当期数据
  → 多表面渲染
  → 发布校验
  → GitHub Release
```

不得为实验建立第二套公司、事件或证据事实库。

## 11. 指标与归因

每天生成一次增长快照，记录：

- 当前 Star、Fork、Watch；
- Release 可用访问数据；
- GitHub 页面访问与引荐来源；
- 已确认外部引用的 URL、作者与首次发现时间；
- 第一期人工审批结果；
- 第二期自动门禁结果与失败原因。

GitHub Traffic 权限不足或字段不可用时写为 `unknown`，不得写成 0。Clone 数据因 Actions checkout 污染，只作为运行诊断，不作为增长指标。

实验结束报告必须给出：

- Star 净增长；
- 有效外部引用数量和公开链接；
- 两期 Release 的访问差异；
- 人工审批与自动发布失败项差异；
- 获得最多访问或引用的信号类型；
- 成功、部分成功或失败的明确判定。

## 12. 降级与错误处理

- LLM 失败时保留结构化事实，不公开不完整中文草稿；
- 单个信源失败只移除受影响条目，不降低证据门槛；
- 少于 3 条时取消自动发布并报告缺口；
- Release 创建失败时保持上一期 Latest 和 README 不变；
- README 更新失败时 Release 仍有效，但健康状态标为 degraded；
- 同一周期重复运行只允许更新未发布草稿，不得创建重复 Release；
- 事件超过 30 天且没有新证据时退出候选；
- 无法确认身份的外部引用进入候选引用，不计入 KPI；
- 任何公共输出部分更新失败时，校验必须能识别表面漂移并阻断后续成功状态。

## 13. 测试与验收

实现前建立至少 10 条正反例组成的 Top Signals gold set，覆盖：

- 完整官方融资或部署事件；
- 独立 `B+B` 证据；
- 单一 B 来源拒绝；
- 主体、日期和金额冲突；
- 泛行业盘点与推测性内容；
- 旧事件新增证据；
- 同公司和同类型配额；
- 少于 3 条的空窗期。

必须验证：

- 相同输入排序结果完全确定；
- 高热度低证据事件被拒绝；
- 第一期无人工批准时不能发布；
- 第二期满足全部条件时可无人值守发布；
- 少于 3 条时第二期只进入 Review；
- Release 或 README 更新失败不会留下错误的 Latest 状态；
- 连续运行两次不会重复创建 Release；
- README、Release 和归档中的主体、日期、标题与顺序一致；
- 指标缺失显示 unknown；
- 现有完整测试、类型检查、`validate:release` 与发布前校验通过。

## 14. 退出与继续条件

实验结果分为：

- **成功**：新增至少 10 Star，且至少 3 位不同外部用户产生有效引用；
- **部分成功**：只达到其中一个目标，保留 Top Signals 内容能力，但先复盘渠道或内容定位；
- **失败**：两个目标均未达到，停止新增增长功能，重新验证目标用户和价值主张。

无论结果如何，都不得用扩大内容数量、降低证据门槛或批量推广来补足指标。
