# Physical AI 双轨公司观察名单设计

日期：2026-08-13  
状态：产品决策已确认，等待规格评审  
目标用户：投资与战略研究者  

## 1. 产品目标

项目从可信资讯库升级为基于公开证据的公司判断产品。系统每周输出一份可追溯、可讨论、可持续跟踪的 Physical AI 公司短名单，帮助用户判断：哪些公司值得开始跟踪，哪些公司的基本面正在被硬证据持续验证，以及下一步应验证什么。

项目不提供买卖建议、目标价、回报预测或确定性投资评级。内部评分只用于筛选候选，公开内容交付入选原因、证据边界、验证点和反证条件。

## 2. 产品原则

- 判断优先于资讯：公开页面交付决策单元，不堆叠新闻。
- 唯一事实出口：所有公开页面只消费规范事实层与发布快照。
- 事实与推断分离：事实逐句绑定引用；方向性结论标记为“AI 研究判断”。
- 关注与证伪并重：每张判断卡同时给出下一验证点和反证条件。
- 自动化受规则约束：AI 生成草稿，确定性门禁决定是否公开。
- 宁缺毋滥：不为填满榜单降低证据门槛。
- 判断可撤回：纠错、降级、证伪和过期均保留版本历史。

## 3. 双轨产品

每期最多展示 10 家公司，两条轨道在同一期互斥。

### 3.1 前瞻雷达

回答：哪些公司值得在市场形成共识前开始跟踪？

入选门槛：

- 公司主体已映射到规范 `companyId`；
- 至少存在一条独立 B 级证据；
- 存在技术路线、团队、资本、合作、客户或人才中的早期高价值信号；
- 所有推断明确标记为“AI 研究判断”；
- 下一验证点、反证条件和有效期完整。

内部前瞻分维度：

- 路线差异化：25%；
- 团队与历史能力：20%；
- 资本、合作及人才信号：15%；
- 潜在价值链位置：15%；
- 信号新颖性：15%；
- 后续可验证性：10%。

### 3.2 验证动量

回答：哪些公司已形成硬证据，并且基本面仍在增强？

入选门槛：

- 至少一条 A 级证据，或两个独立 B 级来源；
- 融资、客户、部署、收入、量产、实机或可复现技术进展至少一类成立；
- 近期存在持续强化或结构性变化，而非一次性曝光；
- 敏感字段通过字段级核验。

内部验证分维度：

- 客户、部署、收入与量产：30%；
- 技术或产品实质进展：20%；
- 资本持续支持：15%；
- 30/90 天连续强化：15%；
- 证据强度：15%；
- 路线与地域多样性：5%。

### 3.3 公开排序

- 不展示精确分数或名次；
- 每条轨道按“重点关注”和“持续观察”分组；
- 同组内优先展示本期发生实质变化、证据更强、影响更大的公司；
- 方法论公开维度、门槛及迁移规则，但不公开精确权重；
- 同一路线原则上不超过当期名单的 40%，重大事件可例外并说明原因。

## 4. 主体范围与配额

可进入公司榜的主体：

- 独立创业公司；
- 上市公司的明确 Physical AI 业务单元；
- 研究机构孵化且已经具备明确商业主体的团队。

纯实验室、论文项目和开源社区不进入公司榜，保留在研究及技术路线板块。主体关系不清、尚未形成规范公司实体的团队留在候选层。大型平台公司仅在进展足以改变竞争格局时入选，避免长期霸榜。

配额规则：

- 总量上限为 10 家；
- 前瞻雷达通常 3–5 家，最低可以为 0；
- 验证动量通常 3–5 家，最低可以为 0；
- 每条轨道最多保留 2 家“持续观察”；
- 不设置地域硬配额；证据和重要性相近时，以路线和地域多样性作为同分项。

## 5. 公司判断卡

每张公开卡固定包含：

1. 为什么现在值得看：本期发生了什么，变化为何重要；
2. 技术路线及关键依赖：模型、数据、硬件、供应链、客户或部署约束；
3. 下一验证点：1–3 条可由公开事实验证的 30–90 天观察项；
4. 反证条件：1–3 条足以降低关注或退出名单的公开条件。

结构化输出约束：

- `whyNow`：最多 120 个中文字符；
- `routeAndDependencies`：最多 160 个中文字符；
- `nextValidationPoints`：每条带截止日期；
- `falsifiers`：必须可由公开事实验证；
- `factReferenceIds`：事实陈述逐句绑定 Event、Claim 或 Research ID；
- `inferenceLabels`：标记 AI 推断；
- `confidence`：高、中、低，仅表达材料完备度；
- `expiresAt`：默认生成后 60 天；
- 保存 `modelVersion`、`promptVersion`、`methodologyVersion`。

禁止生成买入、卖出、目标价、预期回报或确定性市场份额预测。

## 6. 四层数据架构

### 6.1 事实层

`Event`、`Claim`、`Company`、`Route` 只记录可核验事实、来源和证据状态。候选新闻不得成为公开输入。

### 6.2 判断层

`CompanyThesis` 保存 AI 研究判断、下一验证点、反证条件、引用 ID、生命周期和版本信息。判断层不得修改事实层。

建议契约：

```text
CompanyThesis
  thesisId
  companyId
  track: forward-radar | validated-momentum
  lifecycle
  thesisVersion
  whyNow
  routeAndDependencies
  nextValidationPoints[]
  falsifiers[]
  factReferenceIds[]
  inferenceLabels[]
  confidence
  generatedAt
  expiresAt
  modelVersion
  promptVersion
  methodologyVersion
```

### 6.3 发布层

`WatchlistSnapshot` 是不可变的每周发布快照，只引用已通过门禁的判断卡版本，不复制事实或 AI 文案。

```text
WatchlistSnapshot
  week
  snapshotVersion
  methodologyVersion
  generatedAt
  forwardRadar: CompanyThesisRef[]
  validatedMomentum: CompanyThesisRef[]
  changesSinceLastWeek[]
```

README、Pages、公司分享页和 RSS/Atom 必须消费同一发布快照。

### 6.4 历史层

记录判断状态迁移、修订原因、受影响字段、证据引用、模型版本、方法论版本和回滚点。被证伪内容退出当前页面，但保留公开历史。

唯一公开链路：

```text
候选层 → 规范事实层 → 公司判断层 → 周榜快照 → 所有公开页面
```

## 7. AI 自动发布链路

```text
规范事实
→ 双轨候选独立评分
→ AI 按固定 JSON 契约生成草稿
→ 引用、事实、措辞、反证、有效期门禁
→ 生成判断卡版本
→ 生成周榜快照
→ README / Pages / 分享页 / Feed
```

自动发布必须同时满足：

- 主体对应规范 `companyId`；
- AI 输入不包含未晋升候选；
- 中文四字段完整；
- 每条事实陈述都有有效引用；
- 对应轨道证据门槛成立；
- 融资金额、估值、客户、收入和订单经过字段级核验；
- 不存在主体、日期或关键字段冲突；
- 下一验证点、反证条件和有效期齐全；
- 通过投资措辞扫描；
- 相较上期存在实质变化，或属于允许保留的一期。

任何一项失败均不得公开半成品。失败内容进入人工审核队列；已有公开卡继续使用上一个仍然有效的版本。

## 8. 更新节奏

- 每日 08:30：更新事实、证据、公司档案和内部评分；
- 每周一 09:00：生成并发布当期双轨名单；
- 重大事件触发局部重算：融资、并购、量产、订单、核心客户、重大产品或重要反证；
- 单家公司触发后设 6 小时冷却期，避免频繁改版；
- 重大事件修订生成新的快照版本，不覆盖历史周榜；
- 发布失败继续展示上一有效版本，并显示最后成功更新时间。

## 9. 生命周期

公开判断采用六种状态：

- `新进入`：首次达到入选门槛；
- `持续强化`：新增证据继续支持原判断；
- `等待验证`：没有反证，但关键验证点尚未出现；
- `判断降级`：进展弱于预期或证据变弱；
- `已证伪`：反证条件成立，立即退出当前名单；
- `已过期`：60 天没有足够新证据。

迁移规则：

- 同一期双轨互斥；
- 前瞻雷达可以晋升验证动量；
- 验证动量不能退回前瞻雷达，只能等待验证、降级、证伪或过期；
- 已证伪公司再次满足条件时创建新一轮判断，不恢复旧卡；
- 每次迁移必须保存原因和证据引用；
- 首页显示前四种状态，证伪和过期进入公开历史档案。

## 10. 纠错与回滚

- 新证据只重算受影响公司和字段；
- 普通观点变化原位生成新版本，并显示“本次判断为何变化”；
- 主体错配、关键事实错误或核心证据撤回时立即下架当前卡并进入人工复核；
- 用户纠错只能生成待核验 Issue，不能直接修改公开正文；
- 敏感字段修正后必须重新通过字段级核验；
- 每日检查过期、撤稿、失效链接和证据降级；
- 保留最近一次仍有效的判断，不得保留已被证伪的当前结论；
- 严重纠错目标下架时间不超过 30 分钟。

## 11. 公开产品结构

首页顺序：

1. 本周双轨观察名单；
2. 本期判断变化：新增、强化、降级、退出；
3. 公司与资本地图；
4. 技术路线竞争；
5. 学术与研究；
6. 最新规范事实流；
7. 方法论、纠错与贡献入口。

公司详情页展示当前判断、判断历史、技术路线与依赖、资本证据、产品与部署、下一验证点、反证条件以及纠错记录。README 只展示名单摘要与独立分享入口，不复制完整判断卡。

## 12. Watchlist 首版

首版不建设登录和账户系统，提供：

- 一键复制公司研究摘要；
- 公司级 RSS/Atom；
- 技术路线级 RSS/Atom；
- 可复制的 Watchlist 配置链接；
- GitHub Issue 纠错与补证；
- “自上期以来发生了什么”分享页。

首版不提供私人投资组合、收益追踪、团队权限、私密笔记或邮件/即时消息推送。只有当持续跟踪行为被验证后，才评估数据库、登录和协作系统。

## 13. 技术选型

首版保持 Git-native 静态架构：

- TypeScript 作为主语言；
- Git 管理规范 JSON、判断版本和发布快照；
- GitHub Actions 执行每日更新、周榜生成、重大事件重算与发布校验；
- GitHub Pages 承载静态产品；
- GitHub Issue/PR 承载纠错、补证与人工异常复核；
- LLM 只生成符合结构化契约的判断草稿；
- Source Adapter 增加轻量页面内容指纹和语义变化能力；
- 信源可以调用 RSSHub 路由，但不复制 AGPL 实现。

数据规模达到数千事件并需要大量横向分析时，可在 CI 中加入 DuckDB 作为只读分析层，再导出静态 JSON。首版不引入 Postgres、Next.js、用户账户、重型 Agent 编排平台或完整 RSS 阅读器。

## 14. 验收与成功指标

工程与质量指标：

- 自动发布成功率不低于 95%；
- 公开卡引用完整率 100%；
- 主体错配为 0；
- 关键字段冲突泄漏为 0；
- 严重错误下架时间不超过 30 分钟；
- 过期卡残留为 0；
- README、Pages、分享页和 Feed 快照一致率 100%；
- 失败运行不覆盖最近一次有效快照。

产品指标在连续运行四周后评估：

- 每期达到门槛的公司数；
- 公司卡证据展开率；
- 复制或分享率；
- Watchlist 订阅率；
- 两周及四周回访率；
- 用户补证与纠错数量；
- 下一验证点被后续事实命中的比例。

Star、访客来源及分享入口转化单独跟踪，不作为首版产品质量指标。

## 15. 风险边界

- AI 判断可能语言流畅但缺少依据，因此引用完整性和事实一致性是阻断式门禁；
- 单一 B 级证据只允许进入前瞻雷达，不能被表述为已验证动量；
- 评分不能公开包装为投资评级；
- 公司知名度不能替代实际变化；
- 候选层不能直接成为任何公开页面的数据源；
- 周榜稳定性优先于日级排名波动；
- 所有方向性判断必须显示 AI 属性、有效期和反证条件。

## 16. 实施边界与交付顺序

本设计作为一个产品目标交付，但实施计划必须拆成四个可独立验收的阶段，禁止跨层并行写入两套公开真相：

1. **数据契约与迁移**：先落地 `CompanyThesis`、`WatchlistSnapshot`、生命周期、版本及引用契约；将现有公司、事件和路线数据映射到新契约，并保持旧公开页面继续读取最近一次有效数据。
2. **判断生成与质量门禁**：实现双轨候选筛选、结构化 AI 草稿、字段级核验、冲突阻断、投资措辞扫描、过期与反证处理；这一阶段只生成内部预览，不切换公开页面。
3. **统一发布与公开页面**：以不可变快照作为 README、Pages、分享页和 Feed 的唯一输入，一次性切换公开消费者；切换失败必须自动回退到最近一次有效快照。
4. **Watchlist 与运营闭环**：增加公司/路线 Feed、配置链接、复制与分享、Issue 纠错及产品指标；账户、私密数据和收益功能不属于本设计范围。

每个阶段均需完成契约测试、固定夹具测试、快照一致性测试和回滚演练后才能进入下一阶段。实施计划应把现有日报链路视为兼容约束，不得为了双轨名单破坏每日事实更新、候选隔离、公司实体解析、融资二次核验或研究论文更新。
