# 第三期决策产品设计规格

## 1. 背景与目标

第三期不是重新建设资讯首页，而是把现有 Top Signals、公司 Watchlist、研究决策卡和 Feed 能力收敛为一层一致、可校验、可订阅的决策产品。

本期服务两类核心用户：

- 产业与投资研究者：快速判断什么发生了、影响谁、证据是否充分，以及哪些公司与路线正在发生实质变化；
- 研究人员：快速判断一篇论文解决什么问题、是否有真实机器人和基准证据、复现需要什么，以及来自哪些重点作者或实验室。

本期交付四个产品面：

1. 每周 Top Signals；
2. 30 秒公司卡；
3. Research Reproducibility Passport；
4. 零后端订阅中心。

## 2. 设计原则

- **单一事实源**：公开内容只引用规范事件、公司 Claim Ledger、Benchmark Result Ledger、研究决策卡与公开 Watchlist 快照。
- **生成期物化**：排序、字段投影、证据门禁和 unknown 状态在 TypeScript 生成期完成；浏览器只渲染已校验 JSON。
- **事实与判断分离**：事实字段必须携带证据；“为何重要”“下一验证点”等判断字段必须明确标记为研究判断。
- **unknown 不是否定**：没有公开融资、客户、实机或代码证据时显示 unknown，不写成“没有”。
- **零后端**：不采集邮箱，不建立数据库，不引入用户账户；订阅通过 GitHub、RSS/Atom 与可复制筛选链接完成。
- **同源输出**：README 摘要、独立分享页与订阅 Feed 由同一物化合同生成，禁止各自重新排序或推断。

## 3. 非目标

- 不建设登录、邮件发送、支付或推荐系统；
- 不新增人工维护的第二套公司或论文事实库；
- 不允许浏览器从原始候选层临时拼装公开结论；
- 不改变 Phase 2 双账本的字段状态、证据等级或纠错语义；
- 不承诺个性化推送，只提供可保存和可分享的筛选订阅入口。

## 4. 总体架构

每日流水线先完成既有抓取、实体归属、事件与论文核验、双账本生成，再建立统一的决策产品物化层：

```text
规范事件 / 公司 Claim Ledger / Benchmark Ledger / 研究决策卡 / Watchlist
                              ↓
                 Decision Product Materializer
          ┌──────────────┬──────────────┬──────────────┐
          │ Top Signals  │ Company Card │ Repro Passport│
          └──────────────┴──────────────┴──────────────┘
                              ↓
                dashboard.json + feeds manifest
                              ↓
             README / Pages / RSS / 分享筛选链接
```

物化层应由小型、独立模块组成：

- `src/decision-products/top-signals.ts`：筛选并解释本周信号；
- `src/decision-products/company-card.ts`：从公司档案与 Claim Ledger 投影公司卡；
- `src/decision-products/repro-passport.ts`：从研究决策卡与 Benchmark Ledger 投影复现护照；
- `src/decision-products/subscriptions.ts`：生成订阅目录与稳定 Feed 元数据；
- `src/decision-products/contracts.ts`：四类公开合同、严格校验与公共/private 边界；
- `src/decision-products/materialize.ts`：组合上述模块并生成一个事务内的公开产物。

## 5. 每周 Top Signals

### 5.1 合同

每条信号包含：

- 稳定 `signalId`；
- 中文标题和两句以内事实简介；
- 事件类型、技术路线与明确主体；
- 事件发生时间、最后核验时间与是否本周新变化；
- `A` 或独立 `B+B` 证据状态、独立来源数和证据链接；
- 影响对象：公司、资本、产品/部署或研究；
- 明确标记的“为何重要”研究判断；
- 可解释排序分解，不公开一个无法解释的总分。

### 5.2 门槛与排序

- 只接受规范公开事件；单一 B 来源只能进入“正在发生”，不能进入 Top Signals；
- 主体不明确、事实冲突、已撤回、只有发现层来源或缺少中文事实简介的条目不得进入；
- 首先按本周是否发生实质变化排序，其次按证据等级、产业影响、独立佐证和事件新鲜度排序；
- 同一主体、同一事件只保留一条；同一事件类型最多三条；总数最多十条；
- 排序分解必须能从事件和证据字段重新计算，页面不得二次排序。

## 6. 30 秒公司卡

每张公司卡回答五个问题：

1. 公司押注哪条技术路线；
2. 最近一次可核验资本事件是什么；
3. 产品或部署验证到什么阶段；
4. 本周发生了什么变化；
5. 仍有哪些关键字段未知或需要补证。

公司卡包含公司名、地区/阶段、路线、资本状态、产品/部署阶段、最新两条规范事件、字段级证据状态、Watchlist 生命周期、下一验证点与证据入口。没有公开融资证据时显示“证据不足（不代表未融资）”。公司主体、事件归属与 Claim Ledger 不一致时整张卡不得公开。

首屏采用紧凑摘要，展开后显示字段级证据和历史纠错；同一合同同时供首页、`companies.html` 和 README 摘要使用。

## 7. Research Reproducibility Passport

每份护照包含：

- 中文标题与两句事实简介；
- 任务、机器人本体、方法类别；
- 基准、指标、结果、基线与差值；
- 真实机器人试验状态；
- 代码、数据、权重三类复现资产；
- 复现成本等级及其依据；
- 重点作者、实验室、OpenAlex 引用/撤稿状态与元数据核验时间；
- 限制、复现缺口与“为何值得关注”。

Benchmark 数字必须来自 Benchmark Result Ledger；无精确比较证据时保持 unknown。撤稿、OpenAlex 身份冲突或论文卡不完整时不得进入首页六篇研究卡。护照是证据护照，不是论文排行榜；首页排序仍使用已公开的相关性、实机、基准、开源、实验室权威性与时效性规则，并公开排序理由。

## 8. 零后端订阅中心

新增独立订阅入口，提供：

- GitHub Watch、Releases 与仓库 Star 入口；
- 全局 Top Signals Feed；
- 五条规范技术路线 Feed；
- Watchlist 变化 Feed；
- 公司与路线筛选器生成的可复制 URL；
- 每种订阅的内容范围、更新频率和证据门槛说明。

订阅中心不保存用户选择。公司和路线参数沿用现有 Watchlist URL 编解码与白名单；未知公司 ID、非法路线、超长查询和重复值必须被拒绝或规范化。Feed GUID 由规范主体、事件/判断版本和路线构成，固定输入重复生成时字节一致。

## 9. 数据流与事务边界

1. 读取规范事件、公司实体、双账本、研究注册表、决策卡和公开 Watchlist；
2. 构建四类决策产品合同；
3. 运行字段、证据、主体、时间、unknown 和 private-key 校验；
4. 在现有 `FileTransaction` 中同时写入决策产品 JSON、dashboard、Feed 清单和 README 标记区；
5. 任一合同、渲染或交换失败时回滚全部公开产物，保留上一版；
6. `validate:release` 重算核心投影与排序，拒绝页面/Feed/README 漂移。

候选、原始 LLM 输出、OpenAlex 请求正文、内部评分、Review Case 和未晋升判断不得写入公开合同。

## 10. 降级与错误处理

- 本周没有满足门槛的信号时，显示“暂无新增高置信事件”，保留最近一次有效公司卡和研究护照；
- 外部 LLM 或 OpenAlex 降级时，不覆盖已有完整中文卡和已核验元数据；
- Claim Ledger 或 Benchmark Ledger 损坏时停止公开发布，而不是跳过该模块；
- 单一 Feed 渲染失败时整次公开事务回滚；
- 历史订阅 GUID、公司卡 ID 和护照 ID 不随生成时间变化；
- 字段纠错沿用 Phase 2 纠错链，不在第三期另建事实历史。

## 11. 基线阻断与前置修复

最新生产数据已经进入 `2026-W35`，而 `tests/dual-ledger-pipeline.test.ts` 使用 `2026-08-23` 固定时钟并复制整个生产 `watchlist/history`。测试回放 W34 时会生成第二个内容不同的 `2026-W34-v1`，正确触发不可变快照身份冲突。

第三期 Task 0 必须先隔离该测试夹具：固定时钟集成测试不得复制生产 `watchlist/current.json`、`watchlist/theses.json` 或不断增长的 `watchlist/history`，而应创建空历史或显式固定快照。不得放宽 `indexedSnapshots()` 的不可变身份校验。

## 12. 测试与发布校验

每个模块采用测试先行：

- Top Signals：正例、单 B 拒绝、冲突/撤回拒绝、去重、类型配额、固定输入幂等；
- 公司卡：完整卡、unknown 资本、错误事件归属、字段纠错、过期证据；
- 复现护照：完整 Benchmark、unknown 数字、撤稿阻断、资产缺失、OpenAlex 降级；
- 订阅中心：全局/路线/Watchlist Feed、非法筛选、稳定 GUID、字节幂等；
- 集成：公开 JSON、README、Pages 和 Feed 同源，事务中途失败全量回滚；
- 发布：`pnpm run check`、完整测试、`validate:release`、`validate:health`、公开内容门槛扫描与两次固定输入生成；
- 在线：手动触发两次日报，检查生成、提交、Pages、首页日期和第二次去重。

## 13. 验收标准

- 首页和周页最多展示十条完整 Top Signals，所有条目可解释排序且满足证据门槛；
- 至少二十家核心/成长公司可生成结构完整的 30 秒公司卡，缺失字段显式为 unknown；
- 首页六篇研究卡均带 Reproducibility Passport，并能解释为何值得关注；
- 订阅中心提供全局、五条路线和 Watchlist 变化入口，不保存个人数据；
- README、Pages、Feed 与 JSON 对同一条目的主体、日期、状态和链接完全一致；
- 固定输入重复生成字节一致，任一公共产物失败会保留上一版；
- 不新增数据库、账号系统、邮件服务或第二套事实库；
- 完整测试和发布校验通过，线上两次日报均成功。
