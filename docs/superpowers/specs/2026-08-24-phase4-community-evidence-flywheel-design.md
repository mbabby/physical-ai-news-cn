# Phase 4 社区证据飞轮设计

日期：2026-08-24  
状态：已通过产品设计评审，待实施计划

## 1. 目标

第四期第一阶段为项目建立无需独立后台的社区证据飞轮：系统从内部候选层识别一个可在约两分钟内完成的事实缺口，通过 GitHub Issue 自动发布有限数量的补证任务；维护者人工采纳证据后，下一次日报重新核验证据与实体归属，只有满足既有事实门槛的内容才能进入公开产品。

本阶段服务两个目标：

1. 让候选证据缺口持续获得外部补充，而不是依赖维护者逐条检索；
2. 让贡献者获得可追溯、可纠错的公开署名，同时不以数量排名鼓励低质量提交。

## 2. 非目标

本阶段不建设：

- 独立账户、数据库、邮件订阅或外部任务后台；
- 主观技术判断、公司前景评价或投资建议任务；
- 自动接受证据或直接修改公开结论；
- 个性化 Watchlist、变化过滤器、OG 图或 SEO 增长功能；
- 按贡献数量排序的竞争性排行榜。

## 3. 产品原则

- **一个任务只补一个字段。** Issue 不得混合融资金额、客户、代码链接等多个目标。
- **证据接纳不等于事实发布。** `accepted-evidence` 只进入复核输入，不能绕过现有 A 级或独立 B+B 门槛。
- **候选层与公开层隔离。** 候选 ID、内部评分、模型输出和未公开推断不得进入 Issue、网站或贡献账本。
- **未知不是否定。** 没找到证据只能保持 unknown，不能写成“未融资”“没有部署”或“没有代码”。
- **历史可追溯。** 采纳、晋升、纠错、失效和撤回都追加记录，不静默覆盖历史。
- **WIP 优先于吞吐。** 系统维持少量可完成任务，不制造无人维护的 Issue 垃圾场。

## 4. 方案与边界

采用 GitHub 原生架构：

- 每日日报生成经过脱敏的任务种子；
- GitHub Actions 每周查询当前开放任务并补足 WIP；
- GitHub Issues 承载补证协作、人工采纳与审阅记录；
- JSON 账本保存任务、接纳证据和贡献者状态；
- 静态 Pages 展示开放任务与贡献档案；
- 现有 `FileTransaction` 原子发布公开任务和贡献数据。

不新增外部服务。GitHub API 是唯一社区状态来源；仓库内账本是经过校验的可重建投影，不是第二套人工事实库。

## 5. 任务来源

任务生成器扫描三个内部候选池：

1. 公司与融资候选；
2. 产品与部署待核验事件；
3. 论文复现信息缺口。

任务候选必须满足：

- 可以解析到一个规范公司、事件或论文主体；
- 只有一个明确待补字段；
- 至少有一个可公开访问的参考链接；
- 待补内容能够由原始发布、官方页面或独立来源客观确认；
- 不包含终止、撤回、冲突未解决或已过期的上游对象；
- 脱敏后仍具有足够上下文，贡献者无需读取内部文件即可完成任务。

不满足条件的候选继续留在内部 Review 层，不生成公开任务。

## 6. 任务类型

### 6.1 公司与融资证据

允许目标：

- 官方公司名称或官网；
- 融资轮次；
- 融资金额；
- 估值；
- 投资方或监管披露。

优先证据为公司公告、投资方公告或监管文件；权威媒体可以作为独立 B 级证据，但聚合页不能被标记为官方证据。

### 6.2 产品与部署证据

允许目标：

- 官方产品页；
- 产品发布日期；
- 客户名称；
- 部署地点；
- 客户试点或规模部署证据。

演示视频不能自动等同于客户部署，合作声明不能自动等同于商业收入。

### 6.3 研究元数据

允许目标：

- 代码仓库；
- 数据集；
- 模型权重；
- 真实机器人实验；
- 作者或实验室机构信息。

论文摘要里的未来开放承诺不能被当作已发布资产。实验室信息优先使用论文、机构主页或 OpenAlex 等可追溯元数据。

## 7. 两分钟任务合同

每个公开任务包含且只包含：

- 稳定的公开任务 ID；
- 一个任务类型；
- 一个规范主体名称和公开主体链接；
- 一个待补字段；
- 已知事实的简短中文上下文；
- 一至三个已有公开参考链接；
- 推荐查找位置；
- 合格与不合格证据示例；
- 一个结构化回复模板；
- `预计 2 分钟` 提示；
- 生命周期标签和生成周次。

任务正文不得包含内部 seed ID、候选 ID、分数、排名、模型响应、私有诊断或未经证据支持的结论。

## 8. WIP 与调度

公开补证任务的在途上限为 5：

- 公司/融资、产品/部署、研究元数据各预留至少 1 个名额；
- 剩余 2 个名额按产业影响、证据缺口价值和任务可完成性分配；
- 每周定时工作流只补足空位，不固定新增 5 个；
- 同一主体、字段和证据缺口只能存在一个未终止任务；
- 已关闭、已接纳和 stale 任务仍参与稳定 ID 去重，除非上游出现新的材料变化；
- 工作流保留 `dry_run` 和可配置上限，但硬上限始终为 5。

生命周期：

```text
ready → open → contributed → accepted | rejected | stale → closed
```

- 7 天没有有效活动：添加 `stale`；
- 14 天仍无有效证据：关闭并释放 WIP；
- 新材料变化可以产生新版本任务，但必须保留旧任务链接；
- 接纳或拒绝由维护者人工执行。

## 9. 审核与事实晋升

Issue 被标记为 `accepted-evidence` 后：

1. 自动化读取 Issue 作者、被明确采纳的共同补证者、回复中的证据链接和目标字段；
2. 生成严格的 accepted-evidence 输入记录；
3. 下一次日报重新访问证据链接；
4. 重新执行实体解析、来源分级、字段一致性、冲突和时间校验；
5. 证据进入规范候选层；
6. 只有满足现有事实门槛后，才允许更新事件、公司档案、研究卡或首页。

任何阶段失败都不得直接改变公开事实。标签被移除、来源撤回或字段发生冲突时，系统追加纠错状态，并在下一次发布中重新评估受影响内容。

## 10. 贡献者署名

贡献账本记录：

- GitHub 用户名；
- Issue 编号和稳定任务 ID；
- 证据链接；
- 贡献类型；
- 关联公司、事件或论文；
- `submitted`、`accepted`、`promoted`、`corrected`、`withdrawn` 状态；
- 每次状态变化的时间与来源。

Issue 作者在证据被人工采纳后获得署名。评论区补证者只有在维护者通过结构化标记明确采纳其证据时才进入账本。

公开贡献页展示：

- 累计被采纳证据数；
- 融资证据、部署证据、研究元数据分类徽章；
- 最近贡献及其 Issue；
- 已晋升公开内容的链接；
- 后续纠错或撤回状态。

页面不展示 Top 贡献者排名，也不把被采纳数量解释为专业能力评分。

## 11. 数据合同

### 11.1 `review/evidence-task-seeds.json`

日报生成的脱敏任务种子。包含生成时间、周次、精确 schemaVersion 和已排序 seeds。每个 seed 使用规范主体、目标字段和材料变化生成稳定 ID。

### 11.2 `review/evidence-task-ledger.json`

任务生命周期投影。记录 Issue 编号、任务版本、开放/过期/关闭状态和上次有效活动，不保存评论全文。

### 11.3 `review/accepted-evidence.json`

已人工采纳、等待日报复核的证据输入。只保存结构化目标、贡献者、证据 URL、Issue 和采纳时间；原始讨论保留在 GitHub。

### 11.4 `community/contributions.json`

追加式贡献状态账本。相同 Issue、贡献者、证据和目标生成稳定记录 ID；纠错产生新状态记录，不改写旧记录。

### 11.5 `site/data/community-tasks.json`

公开任务与贡献者视图。由前述账本生成，只包含公开安全字段，并与 `site/contribute.html` 使用同一顺序和 ID。

所有合同均使用精确嵌套键、规范 URL/时间、重复 ID 检测和递归私有边界扫描。

## 12. 页面设计

首页增加一个紧凑模块：

- 标题：`帮助完善 5 条物理 AI 情报`；
- 当前开放任务数；
- 本周采纳证据数；
- 本周新增贡献者数；
- 前往贡献中心的入口。

`site/contribute.html` 展示：

- 当前开放任务，按任务类型分组；
- 每项任务的单一目标、预计时间和 Issue 链接；
- 证据门槛说明；
- 最近被采纳的贡献；
- 贡献者分类徽章；
- accepted 不等于自动发布的醒目说明。

候选为空时展示“当前没有达到公开任务门槛的缺口”，不得用低质量任务填充页面。

## 13. 原子性与失败处理

日报在同一个 `FileTransaction` 中暂存任务种子、公开任务视图、贡献账本投影、Dashboard 和页面数据。

以下情况必须保留上一份有效公开数据：

- GitHub API 不可用；
- Issue 数据结构不完整；
- accepted-evidence 解析失败；
- 候选任务包含私有字段；
- 任一输出 swap 失败；
- 任务账本与 GitHub Issue 状态不一致。

任务创建工作流只操作 GitHub Issues，不修改公开事实文件。日报负责将 GitHub 状态重新投影到仓库，避免双向并发写入。

## 14. 校验与纠错

发布校验必须拒绝：

- 候选 ID、内部评分、排名、模型输出或密钥痕迹；
- 一个任务包含多个 targetField；
- 主体与证据页面主体不一致；
- 聚合页面被错误标成官方来源；
- 重复开放任务或超过 WIP 上限；
- stale/closed 任务仍显示为开放；
- accepted 标签已撤回但输入仍被视为有效；
- 未被明确采纳的评论者获得署名；
- 贡献账本删除或改写历史状态；
- accepted evidence 直接进入公开事实而未经过日报核验。

纠错状态采用追加记录，并将受影响的公开内容重新送入现有纠错与 LKG 校验。

## 15. 指标

第一阶段记录以下运营指标：

- 开放任务数和类型覆盖；
- 任务首次响应时间；
- 任务关闭时间；
- 证据接纳率；
- accepted 到 canonical promotion 的转化率和耗时；
- 活跃贡献者与新增贡献者；
- stale/重复/无效任务比例；
- 因社区证据完成的公司、事件或论文字段数。

指标用于评估飞轮是否工作，不作为贡献者个人排名。

## 16. 测试策略

### 单元测试

- 三类候选到任务种子的映射；
- 单一 targetField、稳定 ID、排序和 WIP 配额；
- 脱敏、来源分级、URL 和时间校验；
- 贡献状态追加和分类徽章；
- stale/close/新材料版本逻辑。

### 合同与对抗测试

- 候选 ID、评分、模型文本和多目标泄漏；
- 重复任务、伪造 accepted 标签和错误共同署名；
- 主体错配、撤回链接和聚合源冒充官方源；
- accepted evidence 绕过事实门槛；
- 账本历史删除或重排。

### 集成测试

- 日报生成任务种子与公开投影；
- GitHub Issue dry-run、WIP 补足、去重、7/14 天生命周期；
- accepted evidence 进入下一次日报复核但不直接发布；
- 原子 swap 故障保留上一有效任务和贡献数据；
- 固定输入连续两次输出字节一致。

### 线上验收

- 连续两次 Actions 运行成功；
- 首次最多创建 5 个任务，第二次不重复；
- 手工完成一个沙盒任务的提交、采纳、署名和日报复核链路；
- Pages 贡献中心与 GitHub Issue 状态一致；
- 发布校验与健康检查通过或仅报告明确外部降级。

## 17. 验收标准

本阶段完成必须同时满足：

1. 系统自动维持不超过 5 个开放任务；
2. 有候选时三类任务各至少 1 个；
3. 每个任务只有一个可在约两分钟内完成的目标；
4. 任务和贡献页面不存在私有字段泄漏；
5. Issue 去重、stale 和关闭机制有效；
6. accepted evidence 进入日报复核而不直接公开；
7. 贡献账本、徽章和纠错状态自动更新；
8. 固定输入双跑字节一致；
9. 故障保留上一有效任务与贡献账本；
10. 全量测试、发布校验和两次线上 Actions 通过。

## 18. 后续阶段

完成社区证据飞轮后，第四期按以下顺序继续：

1. 个性化关注公司、技术路线、论文和只看变化视图；
2. 分享卡、OG 图和 SEO；
3. 在数据质量与任务供给稳定后，再评估是否需要外部通知服务。
