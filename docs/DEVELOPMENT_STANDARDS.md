# Stage 4 Development Standards

本文件把已批准的双轨 Watchlist 设计与 Stage 4 实施计划固化为项目开发标准。证据口径与贡献入口仍受 [FACTS_POLICY.md](../FACTS_POLICY.md) 和 [CONTRIBUTING.md](../CONTRIBUTING.md) 约束。若与旧有说明冲突，以本文件、[设计稿](./superpowers/specs/2026-08-13-dual-track-company-watchlist-design.md) 和 [Stage 4 计划](./superpowers/plans/2026-08-13-dual-track-watchlist-stage-4-following.md) 的组合约束为准。

## 1. Scope and source of truth

- Contributors MUST treat this file as the Stage 4 development contract.
- Contributors MUST NOT invent a second public truth source, private shadow store, or alternative publication path.
- Contributors SHOULD reuse existing contracts, snapshot shapes, and validation helpers instead of adding parallel representations.

## 2. Public / private boundary

- Public artifacts MUST contain only canonical public company/thesis/event references, approved facts, public snapshot metadata, and generic evidence gaps.
- Public artifacts MUST NOT contain candidate IDs, internal scores, internal ranks, prompt text, raw model output, discovery-only sources, private notes, or hidden diagnostics.
- GitHub Issues are public review records. They MAY materialize already-public canonical references and generic evidence gaps only.
- Private candidates MUST NOT enter an Issue.
- `accepted-evidence` means review acceptance only. It MUST NOT promote public truth or bypass public publication gates.

## 3. Route and configuration invariants

- The five canonical `TechnicalRoute` names and ASCII slugs are fixed one-to-one:
  - `data-and-training` = `数据与训练`
  - `vla-and-embodied-models` = `VLA 与具身模型`
  - `world-models-and-spatial-intelligence` = `世界模型与空间智能`
  - `embodiment-and-hardware` = `本体与硬件`
  - `deployment-and-commercialization` = `部署与商业化`
- Route URLs, feeds, and shareable configs MUST use the canonical slug table. They MUST NOT derive slugs from display copy or ad hoc normalization.
- Canonical route membership MUST come from public company profiles or public cards only. AI prose MUST NOT invent route membership.
- Stage 4 shareable Watchlist configs MAY contain only company IDs present in the current immutable public Watchlist snapshot and canonical route slugs.
- Unknown, expired, malformed, or malicious config values MUST be ignored with an explicit warning.
- No second company truth source or persistence layer MAY be introduced for share/config decoding.
- Renderers MUST NOT emit arbitrary URLs. A URL MAY be rendered only if it is a validated canonical absolute URL or a deterministic site route derived from approved IDs.

## 4. Snapshot, change pages, and ordering

- Change pages MUST compare adjacent immutable snapshot versions only.
- Same-week version corrections, strengthening, and the `awaiting-validation` lifecycle MUST be derived only from exact thesis versions and canonical evidence.
- Internal scores and ranks MUST NOT appear as public changes.
- Public collections, feeds, change lists, and review outputs MUST use stable code-unit ordering.
- Outputs MUST be idempotent: the same inputs and fixed clock MUST produce byte-identical public files.
- When a rerun has no semantic change, the generated bytes MUST remain unchanged.

## 5. Publication and rollback

- Daily Watchlist outputs, including snapshot, theses, feeds, change page, Watchlist metrics, dashboard, and README, MUST publish through one `FileTransaction`.
- That `FileTransaction` MUST roll back the whole set together if any staged public file fails.
- The separate community-metrics job MUST publish its two mirrors atomically within that job.
- A failed run MUST preserve the last-known-good public outputs.
- Stage 4 public writes MUST use the staged transaction path; partial writes to public artifacts are not acceptable.

## 6. Review automation and GitHub permissions

- Issue automation MUST use least privilege: `contents: read` and `issues: write`.
- Workflows that only create or update review Issues MUST NOT request broader repository permissions.
- Review Issues MUST stay public-review-only. They MUST NOT expose private candidates or internal scoring.
- `accepted-evidence` MAY record review acceptance, but it MUST NOT directly mutate public facts.

## 7. Metrics and null semantics

- Missing traffic, referrer, copy, or share data MUST be represented as `null` plus an explicit availability status.
- Missing observational data MUST NOT be coerced to zero.
- Repository growth metrics MUST remain separate from product-quality metrics.
- Any published rate MUST include both numerator and denominator.

## 8. Verification and release gates

- Contributors MUST use TDD RED/GREEN for every material behavior change.
- A major release MUST pass the full relevant test suite, two deterministic runs with fixed fixtures and clock, and the fault-injection matrix before publication is considered.
- Fault injection MUST cover at least LLM outage, corrupt prior JSON, invalid company ID, evidence withdrawal, source timeout, and transaction swap failure.
- Release validation MUST confirm snapshot/feed identity agreement, config validity, public/private boundary checks, and last-known-good rollback behavior.
- No push or deploy MAY happen without explicit user authorization.
- No secrets MAY appear in logs, generated artifacts, or published output.
- When publication is authorized, contributors SHOULD follow the physical-ai release-validation workflow before pushing or deploying.

## 9. Contributor checklist

- Write the failing test first.
- Confirm the failure before coding.
- Implement the smallest change that makes the test pass.
- Re-run the relevant tests and confirm green.
- Check public/private boundary rules.
- Check deterministic ordering and idempotent output bytes.
- Check transaction staging and rollback behavior.
- Check permissions, logs, and artifact hygiene.
- Check release gates before any major release.

## 10. Phase 2 dual-ledger invariants

- `Company Claim Ledger` and `Benchmark Result Ledger` MUST be rebuilt from canonical company/event and research/decision-card inputs inside the same daily `FileTransaction`.
- Every structured field MUST use exactly one status: `verified`, `developing`, `conflicted`, or `unknown`. Missing evidence MUST remain `unknown`; it MUST NOT be rendered as a negative fact such as “没有融资”.
- Known fields MUST bind direct, non-discovery evidence for that exact field value. A report about an event as a whole MUST NOT verify unrelated amount, round, investor, customer, benchmark, result, or artifact fields.
- Correction IDs and ordering MUST be deterministic. Reordered evidence, citation-count changes, and verification-clock-only updates MUST NOT create a correction.
- Corrupt prior ledger state MUST stop publication. Both ledgers and `review/dual-ledger-metrics.json` MUST roll back together on a transaction failure.
- `Benchmark Result Ledger` is not a ranking or leaderboard. Phase 2 MUST NOT expose an investment ranking, company score, paper score, or new public recommendation surface.
